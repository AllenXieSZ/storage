## 1. 参数规模：架构超参数与存储体积的关系

### 1.1 参数量由什么决定？

参数规模不是固定阶梯，但业界有常见的"甜点"规模。参数量由架构超参数决定：

**Transformer 主要参数来源：**

| 组件 | 参数量公式（近似） | 说明 |
|---|---|---|
| Embedding 层 | V × d | V=词表大小(~32K–150K)，d=隐藏维度 |
| 每层 Self-Attention | 4 × d² | Q/K/V 投影矩阵 + 输出投影，各 d×d |
| 每层 FFN | 8 × d²（标准）或 ~10.67 × d²（SwiGLU，如 LLaMA） | 两层 MLP，中间维度通常 4d |
| LayerNorm | 2 × d × 2（每层两个 LN） | 很小，可忽略 |
| **总参数 ≈** | **V×d + L × (12~14.67) × d²** | L=层数 |

**实际模型对照：**

| 模型 | 隐藏维度 d | 层数 L | 注意力头 h | 参数量 | Checkpoint 大小 (bf16) |
|---|---|---|---|---|---|
| LLaMA-3 8B | 4096 | 32 | 32 | 8B | ~16 GB |
| LLaMA-3 70B | 8192 | 80 | 64 | 70B | ~140 GB |
| LLaMA-3 405B | 16384 | 126 | 128 | 405B | ~810 GB |
| DeepSeek-V3 | 7168 | 61 | 128(MLA) | 671B(MoE 激活37B) | ~1.3 TB |

### 1.2 关键关系

- **参数量 ∝ L × d²**：层数线性、隐藏维度平方。d 翻倍 → 参数翻 4 倍
- 从 7B→70B 不是简单 10 倍层数，而是 d 从 4096→8192（4倍参数）+ 层数 32→80（2.5倍）
- **"阶梯"是人为设计点**，不是物理约束。常见规模 1B/3B/7B/13B/34B/70B/140B/405B/671B(MoE) 是根据 Scaling Law（Chinchilla 法则）和硬件限制选的
- **输入序列长度（context length）不影响参数量**，但影响训练/推理时的激活显存和计算量（注意力计算 ∝ seq_len²）

### 1.3 🗄️ 存储视角

**参数量直接决定 checkpoint 大小**：bf16 下 1B 参数 ≈ 2GB。

| 模型规模 | 模型参数 (bf16) | + 优化器状态 (fp32 m+v) | 完整 Checkpoint |
|---|---|---|---|
| 7B | 14 GB | 28 GB | ~42 GB |
| 70B | 140 GB | 280 GB | ~420 GB |
| 405B | 810 GB | 1620 GB | ~2.4 TB |

训练过程每 500-2000 步保存一次 checkpoint。以 LLaMA-3 405B 为例，390 万步训练，每 1000 步存一次 = 3900 个 checkpoint × 2.4TB ≈ **9.4 PB 的 checkpoint 存储总量**。这就是 FSx Lustre / S3 分层存储（热 checkpoint 放 NVMe tier，冷的通过 DRA 自动归档到 S3）的核心场景。

## 2. 注意力机制：类型、原理与 IO 特征

### 2.1 标准 Multi-Head Attention（MHA）

**原理**：输入 X 分别通过三个线性变换得到 Q（Query）、K（Key）、V（Value），然后：

```
Attention(Q,K,V) = softmax(QK^T / √d_k) × V
```

- 多头：将 d 维拆成 h 个头，每头独立算注意力再拼接，让模型关注不同子空间
- **复杂度**：O(n² × d)，n=序列长度
- **代表**：原始 Transformer、GPT-2/3、BERT

### 2.2 Multi-Query Attention（MQA）

**原理**：所有注意力头**共享同一组 K 和 V**，只有 Q 是多头的。

- **优势**：KV Cache 缩小 h 倍（h=头数，如 32→1），推理时显存占用大幅降低、解码速度更快
- **代价**：质量略降（K/V 信息共享损失表达力）
- **代表**：PaLM、Falcon

### 2.3 Grouped-Query Attention（GQA）

**原理**：MHA 和 MQA 的折中——将 h 个 Q 头分成 g 组，每组共享一套 K/V。g=1 就是 MQA，g=h 就是 MHA。

- **优势**：质量接近 MHA，KV Cache 缩小 h/g 倍
- **代表**：**LLaMA-2 70B、LLaMA-3、Mistral、Claude**（目前主流选择）

### 2.4 Multi-Head Latent Attention（MLA）

**原理**：DeepSeek-V2/V3 提出。不存原始 KV，而是将 KV **压缩到一个低维潜在向量**（latent），推理时从潜在向量恢复 KV。

- **优势**：KV Cache 比 GQA 还小（压缩到约 5%），同时保持完整多头的表达力
- **代表**：DeepSeek-V2/V3/R1

### 2.5 Sliding Window Attention（SWA）

**原理**：每个 token 只关注周围固定窗口（如 4096）内的 token，而非全序列。

- **优势**：计算量从 O(n²) 降到 O(n × w)，支持超长上下文
- **代表**：Mistral（交替层用 SWA + 全注意力）

### 2.6 Sparse Attention / Ring Attention

- **Sparse**：只计算特定模式的注意力（局部+全局+随机），代表 BigBird、Longformer
- **Ring Attention**：将长序列分块分布到多设备上，KV 以"环"形式传递，每设备只算局部
- **适用**：超长文档（100K+ tokens）

### 2.7 Flash Attention（计算优化，非注意力变体）

**原理**：标准注意力的 **IO 优化实现**——将 QKV 分块（tiling），让计算尽量在 GPU SRAM（高速缓存，约 20MB）内完成，避免反复读写 HBM（GPU 显存，如 H100 的 80GB HBM3）。

- **效果**：不改数学结果，纯靠减少显存读写次数加速 2-4x，还支持更长序列
- **核心思想**：标准注意力要把 n×n 的注意力矩阵写到 HBM 再读回来做 softmax，Flash Attention 分块在 SRAM 算完直接输出

### 2.8 🗄️ 存储视角

**注意力机制的选择直接影响推理时的 KV Cache 大小和训练时的激活显存：**

| 注意力类型 | KV Cache（相对 MHA） | 推理显存影响 |
|---|---|---|
| MHA | 1× (基准) | 长上下文时 KV Cache 可达数十 GB |
| MQA | 1/h（如 1/32） | 显著减少，但质量略降 |
| GQA (g=8) | g/h（如 8/64 = 1/8） | 主流选择，质量与效率平衡 |
| MLA | ~1/20 | 最小，但计算恢复 KV 有额外开销 |

Flash Attention 的核心思想——**减少数据搬运，让计算在高速缓存内完成**——跟存储领域减少 NFS/Lustre 元数据往返是同一个道理。GPU 训练的瓶颈越来越不是算力，而是 HBM 带宽（数据搬运速度）。

## 3. 位置编码与 Token 编码

### 3.1 Token 编码（Token Embedding）

把离散 token ID 映射成稠密向量。例如 token "猫" → ID 15432 → 查 Embedding 表第 15432 行 → 得到一个 d 维向量（如 4096 维）。**这是"语义信息"。**

### 3.2 位置编码（Positional Encoding）

Transformer 的 Self-Attention 是**集合运算**——"猫吃鱼"和"鱼吃猫"如果不加位置信息，注意力看到的是一样的。位置编码给每个位置注入"我是第几个 token"的信息。

### 3.3 主流方案对比

| 方案 | 原理 | 外推能力 | 代表模型 |
|---|---|---|---|
| **正弦位置编码** | 固定的 sin/cos 函数，不可学习。加到 token embedding 上 | 较差，超出训练长度质量下降 | 原始 Transformer、BERT |
| **可学习位置编码** | 位置 embedding 作为可训练参数 | 差，只能用训练过的位置 | GPT-2 |
| **RoPE（旋转位置编码）** | 不加到 embedding 上，而是在计算 Q·K 时**旋转** Q 和 K 的向量，使相对位置信息自然编码进点积结果 | **好**，可通过调基频 θ 外推到更长序列（NTK-aware、YaRN） | **LLaMA、Mistral、Qwen、DeepSeek**（当前主流） |
| **ALiBi** | 不加 embedding，直接在注意力分数上**减去与距离成正比的偏置**（越远扣分越多） | 好，天然外推 | Falcon、BLOOM |

### 3.4 各家不统一

- **LLaMA/Mistral/Qwen/DeepSeek**：RoPE（当前绝对主流）
- **Claude**：未公开，大概率 RoPE 或其变体
- **GPT-4**：未公开
- **Falcon/BLOOM**：ALiBi
- **Google Gemini**：未公开

**RoPE 为什么赢了**：它把位置信息编码为旋转角度，Q·K 的点积自然包含相对距离信息 cos(θ(m-n))，数学优雅且支持通过修改 θ 基频（从 10000 提高到 500000 甚至 10M）外推到很长的上下文。

## 4. 前向传播与反向传播

### 4.1 前向传播（Forward Pass）

数据从输入到输出**正向流过**网络：

```
Token IDs
  → Embedding + 位置编码
  → [Layer 1: Attention → FFN]
  → [Layer 2: Attention → FFN]
  → ...
  → [Layer L: Attention → FFN]
  → 输出 logits
  → softmax
  → 预测的下一个 token 概率
```

- 每层的输出是下层的输入，一路向前
- 计算损失：预测的概率分布 vs 真实的下一个 token → **交叉熵损失**（Cross-Entropy Loss）
- 这一步就是"用当前参数做一次推理，看错了多少"

### 4.2 反向传播（Backward Pass / Backpropagation）

从损失出发，**链式法则**反向计算每个参数的梯度：

```
Loss
  → 对 Layer L 输出求导
  → 对 Layer L 参数求导
  → 对 Layer (L-1) 输出求导
  → ...
  → 对 Layer 1 参数求导
  → 对 Embedding 求导
```

- **链式法则**：∂Loss/∂W₁ = (∂Loss/∂output) × (∂output/∂layer_L) × ... × (∂layer_1/∂W₁)
- 每个参数得到一个梯度值，表示"这个参数往哪个方向调能减少损失"
- 然后优化器（如 AdamW）根据梯度更新参数：W_new = W_old - lr × gradient

### 4.3 🗄️ 存储视角

| 阶段 | 显存占用 | IO 特征 |
|---|---|---|
| 前向传播 | 需保存每层**激活值**（中间结果）供反向用 | 纯 GPU 计算，无磁盘 IO |
| 反向传播 | 读取保存的激活值 + 计算梯度 | 纯 GPU 计算，约前向 2× 计算量 |
| 激活重计算 | 用时间换空间：不保存激活，反向时重新前向算 | 减少显存占用 33-50%，代价是多一次前向 |
| 激活 Offload | 激活写到 CPU 内存甚至 NVMe SSD | **产生 PCIe/NVMe IO**，需要高带宽（GPU↔CPU 64GB/s PCIe 5.0） |

70B 模型推理只需 ~140GB 显存，但训练需要 >1TB（参数 + 优化器状态 + 激活 + 梯度）。这就是为什么训练需要模型并行（把模型切到多张卡上）和 ZeRO（分布式优化器状态）。

## 5. Step、Epoch 与训练规模

### 5.1 定义

- **1 step** = 处理 1 个 batch 的数据（前向 + 反向 + 参数更新）
- **1 epoch** = 把**所有训练数据过一遍**

```
Steps per epoch = 总 token 数 / (batch_size × seq_len)
```

### 5.2 实际规模

| 模型 | 训练数据 | Global Batch Size (tokens) | 估算 Steps/Epoch | 实际训练 |
|---|---|---|---|---|
| LLaMA-3 405B | 15.6T tokens | ~4M tokens/step | ~3,900,000 步 | ~1 epoch |
| GPT-4 | ~13T tokens (推测) | — | — | ~1 epoch |
| DeepSeek-V3 | 14.8T tokens | 约 60M tokens/step | ~250,000 步 | ~1 epoch |

**大模型预训练通常不跑完 1 个 epoch**——数据太多，跑 1 遍就够了（甚至跑不完）。训练量用"总 token 数"衡量，不用 epoch。

**微调（Fine-tuning）则不同**：数据可能只有 10K~100K 条，1 epoch 几百 step，通常跑 3-10 个 epoch。

### 5.3 🗄️ 存储视角：训练数据的 IO 模式

| 阶段 | 数据量 | 读取模式 | 存储需求 |
|---|---|---|---|
| **预训练数据加载** | 15T+ tokens (~30TB 原始文本, tokenize 后 ~几 TB) | **纯顺序大块读**，多 worker 并行预取 | 高吞吐（几十 GB/s），延迟不敏感 |
| **Checkpoint 写入** | 每次 400GB-2.4TB | 几百个分片**并发写**，同步阻塞训练 | 高写吞吐 + 低延迟（DCP 异步写阻塞仅 ~0.4s） |
| **Checkpoint 读取（恢复）** | 同上 | 几百个分片**并发读** | 高读吞吐（恢复越快 GPU 空闲越短） |
| **数据 Shuffle** | 按 epoch 打乱顺序 | 随机读 / 预 shuffle 后顺序读 | 预 shuffle 存多份 → 用空间换随机 IO |

**每 N 步做一次 checkpoint**（通常每 500-2000 步）。390 万步 / 1000 = 3900 次 checkpoint。这是 FSx Lustre 在 AI 训练中的核心存储负载。

## 6. NaN / Inf 与梯度异常

### 6.1 什么是梯度

反向传播算出来的"每个参数该往哪调、调多少"的值（偏导数）。

### 6.2 NaN / Inf 的含义与常见原因

训练中出现 NaN（Not a Number）/ Inf（Infinity）意味着**数值爆炸或坍塌**，是训练事故：

| 现象 | 原因 | 解释 |
|---|---|---|
| **梯度爆炸** | 梯度值越来越大 → 超过 fp16 最大值（65504）→ Inf → Inf × 0 = NaN | 深网络反向传播时梯度逐层相乘，若每层 >1 则指数增长 |
| **学习率过大** | 参数更新步子太大 → 损失不降反升 → 参数跑到极端值 → 溢出 | W = W - lr × grad，lr 太大参数"飞出去" |
| **fp16 精度不够** | fp16 动态范围小（±65504），梯度或激活超范围 | 解法：bf16 或 fp16 + loss scaling |
| **数据异常** | 输入中有极端值 / 除零 | softmax 分母为 0、log(0) 等 |
| **Loss spike** | 训练中损失突然飙升 → 梯度暴涨 → NaN | 坏数据 batch 或学习率调度问题 |

### 6.3 防护措施

- **Gradient Clipping**：梯度范数超过阈值（如 1.0）就等比缩放 → 防爆炸
- **bf16（bfloat16）**：跟 fp32 一样的指数位（8 bit），动态范围大，几乎不会溢出，代价是精度略低（尾数 7 bit vs fp16 的 10 bit）。现在训练基本都用 bf16
- **Loss Scaling**（fp16 专用）：前向时把 loss 乘一个大数（如 1024），梯度等比放大（避免 fp16 下溢），更新前再除回来
- **NaN 检测 + 跳过**：发现 NaN 就丢弃该 step 不更新参数，回滚到上一个好的 checkpoint

### 6.4 bf16 vs fp16 vs fp32

| 格式 | 符号位 | 指数位 | 尾数位 | 动态范围 | 精度 | 大小 |
|---|---|---|---|---|---|---|
| fp32 | 1 | 8 | 23 | ±3.4×10³⁸ | 高 | 4 字节 |
| fp16 | 1 | 5 | 10 | ±65504 | 中 | 2 字节 |
| bf16 | 1 | 8 | 7 | ±3.4×10³⁸ | 低 | 2 字节 |

bf16 的指数位与 fp32 相同 → 动态范围一样大 → 训练不容易溢出。这就是为什么 H100/A100 都原生支持 bf16。

### 6.5 🗄️ 存储视角

NaN 导致训练中断 → **回滚到上一个好的 checkpoint** → checkpoint 的可靠写入和快速读取是训练恢复的关键。

- 每次 NaN 回滚 = 重新从 Lustre 读取几百 GB ~ 几 TB 的 checkpoint → 需要高读吞吐
- 如果 checkpoint 写入不完整（写到一半节点挂了）→ 需要更早的 checkpoint → 保留多版本的重要性
- 实测数据：FSx Lustre DCP 异步 checkpoint 写入阻塞仅 0.43s（22.5 GB/s），同步写入也能达到基线吞吐的 94%

## 7. 学习率调参策略

### 7.1 主流方案：Warmup + Cosine Decay

**"先小→大→逐渐变小"是当前标准做法：**

```
学习率
  ^
  |        ╱‾‾‾‾╲
  |       ╱       ╲
  |      ╱         ╲
  |     ╱            ╲
  |    ╱               ╲___________
  |   ╱
  └──╱──────────────────────────────→ step
    warmup   peak        cosine decay → 最终 lr
```

三阶段：

1. **Warmup（热身，先小到大）**：前 ~2000 步，学习率从 ~0 线性增到峰值。刚开始参数随机、梯度不稳定，大学习率会直接 NaN。先小步试探，让参数"找到方向"
2. **峰值阶段**：学习率维持在峰值或直接开始衰减
3. **Cosine Decay（余弦衰减，逐渐变小）**：学习率按余弦曲线平滑降到最小值（通常 peak/10）。后期模型接近最优解，大步长会在最优点附近震荡，小步长才能精细收敛

### 7.2 为什么不"一直大"或"一直小"？

- 一直大 → 后期震荡不收敛，甚至 NaN
- 一直小 → 训练极慢，几百万步走不到好解
- 先大后小（无 warmup）→ 开头就炸

### 7.3 优化器的自适应机制

学习率调度是"全局"的，优化器在**每个参数**级别还有自适应：

**AdamW（当前标准优化器）核心机制：**
- 维护每个参数的 **一阶矩 m（梯度的滑动平均）** 和 **二阶矩 v（梯度平方的滑动平均）**
- 实际更新：`W -= lr × m / (√v + ε)`
- 意思是：**梯度大且稳定的参数 → 步子适中；梯度波动大的参数 → 自动缩小步子**
- 这就是"自适应"——不同参数自动用不同的有效学习率

### 7.4 各家实际配置

| 模型 | 优化器 | 峰值 lr | Warmup Steps | 衰减方式 | 最终 lr |
|---|---|---|---|---|---|
| LLaMA-3 405B | AdamW | 8×10⁻⁵ | 8000 | Cosine | 8×10⁻⁶ (peak/10) |
| LLaMA-3 8B | AdamW | 3×10⁻⁴ | 8000 | Cosine | 3×10⁻⁵ (peak/10) |
| DeepSeek-V3 | AdamW | 2.2×10⁻⁴ | 2000 | Cosine | 2.2×10⁻⁵ (peak/10) |
| GPT-3 175B | Adam | 6×10⁻⁵ | ~375M tokens | Cosine | — |

**规律**：模型越大 → 峰值学习率越小（参数多，每步影响大，要温柔些）。

### 7.5 其他调度方式

- **线性衰减**：warmup 后线性降到 0。简单但中间阶段 lr 可能降太快
- **多阶段阶梯（Step Decay）**：特定 step 直降（如×0.1）。CV 领域常见，LLM 少用
- **WSD（Warmup-Stable-Decay）**：MiniCPM 提出，warmup → 长时间稳定 lr → 最后急速衰减。优势是中间可随时停
- **无衰减 + 大 batch**：部分研究发现足够大 batch 时 lr 可以不衰减，不是主流

## 8. 评估与重新训练：从哪里开始？

评估后发现问题需要重新训练，具体从哪里开始取决于**发现了什么问题**。

### 8.1 从头开始（From Scratch）—— 极少数情况

**触发条件：**
- 数据集有严重问题（有毒数据、版权风险）→ 必须换数据重训
- 架构设计缺陷（MHA→GQA、改 tokenizer/词表）→ 旧 checkpoint 参数形状对不上
- Scaling Law 实验阶段：小规模多组实验，选最佳配置

**代价极大**：LLaMA-3 405B 预训练约 3000 万 GPU 小时（H100），估算 $3000 万+。

**实际案例**：LLaMA-1 → LLaMA-2 → LLaMA-3 每代都是从头训（数据量/tokenizer/架构都变了）。同一代之内一般不会从头来。

### 8.2 从 Checkpoint 继续（Continue Pre-training / Resume）—— 最常见

#### 8.2a 训练中断 → 恢复

最直白的场景：硬件故障、NaN 爆炸、集群维护。

```
Step 0 ────── Step 150,000（NaN 爆炸）
                    ↓
            回滚到 Step 149,000 的 checkpoint
            (可能调小学习率、跳过坏 batch)
                    ↓
            从 Step 149,000 继续 ────── Step 300,000 ...
```

**恢复时加载的完整 checkpoint 包含：**
- 模型参数（bf16）
- 优化器状态（fp32 的一阶矩 m + 二阶矩 v，体积 ≈ 2× 模型参数）
- 学习率调度器状态（当前 step 数 → 恢复正确的 lr）
- 数据加载器状态（RNG seed + 已消费的 sample 索引 → 避免重复/遗漏数据）
- 随机数种子（保证可复现）

这就是为什么完整 checkpoint 那么大：70B 模型参数 140GB + 优化器 280GB = ~420GB。

#### 8.2b 评估后回退到较早 Checkpoint

```
Step 0 ── Step 100K（评估还行）── Step 200K（质量下降/某能力退化）
                ↓
          回退到 Step 100K
          调整：换数据配比 / 调 lr / 改正则化
                ↓
          从 Step 100K 重新跑 ── Step 200K'（新分支）
```

**真实案例**：训练中期评估发现代码能力下降 → 回退，增加代码数据占比，继续训。

### 8.3 后训练（Post-Training）—— 最常见的"改进"方式

预训练完成后，模型只是一个"续写机器"。后训练把 base model 变成好用的产品：

```
Pre-training（万卡跑几个月，15T tokens）
        ↓
    Base Model（如 LLaMA-3-405B-Base）
        ↓
    ┌─────────────────────────────────────┐
    │  Post-Training（后训练）              │
    │                                     │
    │  1. SFT（Supervised Fine-Tuning）   │  ← 人工标注的指令-回答对（~100K-1M 条）
    │     教会模型"听懂人话、好好回答"        │    微调几千步，lr 比预训练小 10-100 倍
    │                                     │
    │  2. RLHF / DPO（对齐）              │  ← 人类偏好数据（好回答 vs 坏回答）
    │     教会模型"什么是好回答"             │    强化学习或直接偏好优化
    │                                     │
    │  3. 专项能力增强                     │  ← 代码/数学/工具调用的专项数据
    │                                     │
    └─────────────────────────────────────┘
        ↓
    Chat Model（如 LLaMA-3-405B-Instruct）
```

**预训练 vs 后训练对比：**

| | 预训练 | 后训练（SFT/RLHF） |
|---|---|---|
| 数据量 | 15T tokens | 10M-100M tokens（少 100-1000 倍） |
| 计算量 | 3000 万 GPU 小时 | 几万 GPU 小时（少 1000 倍） |
| 学习率 | 峰值 ~1e-4 | ~1e-5 到 1e-6（小 10-100 倍） |
| 目标 | 学会语言和知识 | 学会"怎么用"知识、对齐人类偏好 |
| 耗时 | 几个月 | 几天到几周 |
| 改动幅度 | 参数全量大幅更新 | 参数微调，幅度小 |

**评估后"重新后训练"是常规操作**——每次都从同一个 base model checkpoint 出发，调数据配方、调超参数，跑几天看效果。比从头预训练便宜 1000 倍，所以大厂会在后训练阶段做大量实验（Meta 公开说 LLaMA-3 做了 6 轮以上 RLHF 迭代）。

### 8.4 决策树

```
评估发现问题
    │
    ├─ 架构/tokenizer 要改？ ──── 是 → 从头预训练（极贵）
    │
    ├─ 预训练数据要改？
    │     ├─ 小改（调配比） → 从中间 checkpoint 继续
    │     └─ 大改（换数据源） → 可能要从头
    │
    ├─ 预训练 loss 正常，但下游任务不行？
    │     └─ 后训练阶段解决（SFT/RLHF，几天搞定）
    │
    ├─ 训练中 NaN / loss spike？
    │     └─ 回退最近的好 checkpoint，调 lr / 跳过坏数据，继续
    │
    └─ 想加新能力（新语言/新领域）？
          └─ Continue Pre-training 或 LoRA/QLoRA 微调
```

### 8.5 🗄️ 存储视角

- **Checkpoint 是训练的"存档点"**，保留多个历史版本 = 保留回退能力
- 大厂保留策略：热的最近几个放 FSx Lustre（NVMe tier），冷的归档到 S3（通过 DRA 自动导出）
- 后训练阶段 checkpoint 大小相同（同一个 base），但迭代次数多（几十轮实验）→ 版本管理重要

## 9. 存储视角总结：训练各阶段的 IO 特征

### 9.1 训练一步的完整流程

```
[训练数据 batch]                           ← 从 Lustre/S3 读取
   → 前向传播（过所有层，算 loss）            ← 纯 GPU 计算
   → 反向传播（链式法则，算每个参数的梯度）     ← 纯 GPU 计算（约前向 2×）
   → 梯度裁剪（防 NaN/Inf）                  ← GPU 计算
   → All-Reduce（多卡同步梯度）               ← 网络 IO（EFA/InfiniBand）
   → AdamW 优化器更新参数                    ← GPU 计算
   → (每 N 步) 写 Checkpoint                 ← 存储写 IO（Lustre/S3）
```

### 9.2 各阶段 IO 特征对照

| 训练阶段 | 读写模式 | IO 大小 | 并发度 | 延迟敏感 | 推荐存储 |
|---|---|---|---|---|---|
| **数据预取** | 顺序大块读 | MB~GB 级块 | 高（多 DataLoader worker） | 否 | Lustre (高吞吐) / S3 |
| **Checkpoint 同步写** | 并发分片写 | 每分片 ~1GB | 数百并发 | **是**（阻塞训练） | Lustre NVMe (低延迟 + 高吞吐) |
| **Checkpoint 异步写** | 后台并发写 | 同上 | 同上 | 否（仅 flush 阻塞 ~0.4s） | Lustre |
| **Checkpoint 归档** | 大文件写 S3 | 数百 GB | 中 | 否 | S3 (DRA 自动导出) |
| **恢复读取** | 并发分片读 | 数百 GB~TB | 数百并发 | **是**（GPU 空闲等待） | Lustre NVMe |
| **后训练数据** | 随机/顺序读 | KB~MB 级 | 低 | 否 | EBS / Lustre / S3 均可 |
| **Evaluation** | 顺序读（测试集） | 小 | 低 | 否 | 任意 |

### 9.3 FSx Lustre 在 AI 训练中的核心价值

1. **Checkpoint 写入**：分布式并行文件系统，数百 GPU 节点同时写分片，聚合吞吐可达 TB/s 级。同步 checkpoint 阻塞训练时间从分钟级降到秒级 → GPU 利用率从 ~90% 提升到 ~98%
2. **数据预取**：Lustre 的条带化 + 多 OST 并行 → 高聚合吞吐，满足 DataLoader 的带宽需求
3. **S3 分层**：热数据在 Lustre NVMe tier，冷 checkpoint 通过 Data Repository Association（DRA）自动归档到 S3 → 成本优化
4. **恢复速度**：NaN/故障后从 Lustre 读取 checkpoint 恢复，比从 S3 拉取快一个数量级 → 减少 GPU 空闲时间（GPU 小时 = 💰）

GPUDirect Storage (GDS) 数据路径示意

GDS 绕过 CPU bounce buffer,让存储数据直达 GPU 显存 · AWS P5/P6 + EFA + 同 AZ FSx Lustre 实测(2026-07-29)

传统路径（-x 1 CPUONLY）：两跳，经 CPU bounce buffer

数据先 DMA 到 CPU 主机内存的 bounce buffer,再从内存拷到 GPU 显存(两跳)。
代价:多一次内存拷贝,消耗 CPU 周期 + 主机内存带宽。
但 命中 page cache 时反而快(数据已在内存,少了存储读)。

GDS 路径（-x 0 GPUDirect）：一跳直达 DMA

数据由 DMA 引擎直接从存储写入 GPU 显存,完全绕过 CPU 主机内存(一跳)。
价值:消除 bounce buffer,省 CPU 周期 + 主机内存带宽。
⚠️ 吞吐不一定更高:因绕过内存 = 也绕过 page cache。
# 1) 验证平台支持 GDS gdscheck -p # 看 "GPU supports GDS" + "Platform verification succeeded" # 2) gdsio 基准：先写后读（读测试要求文件先存在） gdsio -D /fsx/gdstest -d 0 -w 8 -s 10G -i 1M -I 1 -x 0 # 写, -x 0 = GPUDirect(GDS) gdsio -D /fsx/gdstest -d 0 -w 8 -s 10G -i 1M -I 0 -x 0 # 读, GPUDirect 路径 gdsio -D /fsx/gdstest -d 0 -w 8 -s 10G -i 1M -I 0 -x 1 # 读, -x 1 = CPUONLY 对照组 # 3) 公平对比：清 page cache + 看 CPU 占用 echo 3 | sudo tee /proc/sys/vm/drop_caches # 清缓存, 否则 CPUONLY 命中 cache 不公平 mpstat 1 # 观察 GDS 是否真的省了 CPU # 前置(DLAMI base-oss-nvidia-driver-gpu-ubuntu-24.04)：nvidia-fs 内核模块需手动 build git clone ...gds-nvidia-fs && make && sudo insmod nvidia-fs.ko # apt 装 nvidia-gds 会拉错内核 flavor

⚠️ 依赖关系要分清：在 AWS FSx for Lustre 上 GDS 依赖 EFA（官方「builds on EFA」，跨网络存储→远程 GPU 需 EFA 数据面）；但 GDS 技术本身（NVIDIA Magnum IO）不内在要求 EFA——本地 NVMe→GPU 直连场景就无需 EFA。EFA=AWS 网络协议，GDS=NVIDIA 存储协议，不同层面。
维度传统路径 (-x 1 CPUONLY)GDS 路径 (-x 0 GPUDirect)
数据路径存储 → CPU 内存 → GPU（两跳）存储 → GPU 显存（一跳直达 DMA）
CPU / 内存带宽消耗（多一次内存拷贝）省（绕过主机内存）
page cache可命中 → 可能更快绕过 → 无缓存红利
实测吞吐基准（命中 cache 时占优）反比 CPUONLY 低 ~7%（因绕过 cache）
真正价值—高吞吐(几十~上百 GB/s)或 CPU 忙时省 CPU/内存带宽
结论要点：GDS 吞吐不一定比 CPU 路径高（实测 GPUDirect 反比 CPUONLY 低约 7%,因 CPUONLY 命中 page cache 而 GDS 故意绕过主机内存）。GDS 的价值是消除 CPU bounce buffer、省 CPU 周期与主机内存带宽,只在高吞吐或 CPU 繁忙场景才体现优势。公平对比必须 drop_caches + 用 mpstat 看 CPU 占用。

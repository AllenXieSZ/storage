# 内核解压 / git clone —— 5 客户端并发存储基准测试（EFS vs S3 Files vs JuiceFS）

五台 EC2 客户端在**同一时刻**并发访问**同一个共享文件系统**，各自写入自己的 `clientN/` 子目录。
本测试测量各共享网络存储在 5 路并发下的扩展能力（聚合吞吐 + 元数据竞争），而非五次独立的单客户端测试。

## 测试环境

| 项目 | 值 |
|---|---|
| 区域 | us-east-2（俄亥俄），单可用区（us-east-2a） |
| 客户端 | 5× c7i.4xlarge（16 vCPU，32 GiB），Amazon Linux 2023 |
| Redis 节点（JuiceFS 元数据） | 1× c7i.4xlarge（5 客户端共享） |
| Phase 1 负载 | `tar xf linux-7.2.5.tar.xz` 解压到 `clientN/`（5 客户端同时） |
| Phase 2 负载 | `git clone` 本地 NixOS/nixpkgs 引用仓库到 `clientN/nixpkgs`（5 客户端同时） |
| 方法 | 每轮前清 page cache；统一起跑时刻；记录每客户端墙钟时间 |

每个存储都是**一个共享文件系统**，由 5 台客户端同时挂载：
- **EFS（Bursting）** —— Bursting 吞吐模式，NFSv4.1，全新（满 burst credit）
- **EFS（Elastic）** —— Elastic 吞吐模式，NFSv4.1
- **S3 Files** —— NFS，关联一个开启版本控制的 S3 桶（前缀 `s3files/`）
- **JuiceFS** —— 一套共享 Redis 元数据 + 一个共享 S3 桶，5 客户端全部 FUSE 挂载

每客户端文件数：Phase 1 = **94,758 文件/客户端**（tar）；Phase 2 = **54,447 文件/客户端**（clone）。
"最慢"= 5 个客户端中最后完成的那个 = 真正的并发完成时间。

## 结果 —— Phase 1：`tar xf`（5 客户端并发）

| 存储 | 最快客户端 | 平均 | **最慢（并发完成）** | vs EFS Bursting | 文件/客户端 |
|---|---|---|---|---|---|
| EFS（Bursting） | 2235.3 s | 2281.2 s | **2314.6 s**（38 分 35 秒） | **1.00×**（基准） | 94,758 |
| EFS（Elastic） | 2401.7 s | 2422.2 s | **2438.8 s**（40 分 39 秒） | 1.05× | 94,758 |
| S3 Files | 2431.8 s | 2443.0 s | **2457.8 s**（40 分 58 秒） | 1.06× | 94,758 |
| JuiceFS | 3740.0 s | 3797.0 s | **3859.9 s**（1 小时 4 分 20 秒） | 1.67× | 94,758 |

## 结果 —— Phase 2：`git clone`（5 客户端并发）

| 存储 | 最快客户端 | 平均 | **最慢（并发完成）** | vs EFS Bursting | 文件/客户端 |
|---|---|---|---|---|---|
| EFS（Bursting） | 903.3 s | 922.6 s | **938.1 s**（15 分 38 秒） | **1.00×**（基准） | 54,447 |
| EFS（Elastic） | 998.2 s | 1028.3 s | **1047.6 s**（17 分 28 秒） | 1.12× | 54,447 |
| S3 Files | 1047.4 s | 1053.2 s | **1061.5 s**（17 分 42 秒） | 1.13× | 54,447 |
| JuiceFS | 1954.8 s | 2002.9 s | **2028.4 s**（33 分 48 秒） | 2.16× | 54,447 |

## 并发扩展 vs 单客户端基线

单客户端参考时间来自此前的 `kernel-untar-bench-4way` 测试（一个客户端，同类负载）。
核心问题：5 路并发是否会拖慢每个客户端？

**Phase 1（`tar xf`）** —— 每客户端最慢 vs 单客户端基线：

| 存储 | 单客户端 | 5 客户端最慢 | 变慢倍数 |
|---|---|---|---|
| EFS（Bursting） | 2497 s | 2314.6 s | ~0.93×（无变慢） |
| EFS（Elastic） | 2392 s | 2438.8 s | ~1.02×（持平） |
| S3 Files | 2408 s | 2457.8 s | ~1.02×（持平） |
| JuiceFS | 3617 s | 3859.9 s | ~1.07×（轻微） |

**Phase 2（`git clone`）** —— 每客户端最慢 vs 单客户端基线：

| 存储 | 单客户端 | 5 客户端最慢 | 变慢倍数 |
|---|---|---|---|
| EFS（Bursting） | 992 s | 938.1 s | ~0.95×（无变慢） |
| EFS（Elastic） | 1009 s | 1047.6 s | ~1.04×（持平） |
| S3 Files | 1036 s | 1061.5 s | ~1.02×（持平） |
| JuiceFS | 1982 s | 2028.4 s | ~1.02×（持平） |

## 结论

**四种共享存储在 5 客户端并发下基本都是线性扩展** —— 每个客户端的完成墙钟时间与单客户端独跑时几乎一致，
即**5 倍的聚合工作量，几乎没有每客户端的额外惩罚**。该负载是"每文件延迟"受限（每个小文件创建一次元数据往返），
每个客户端维持自己独立的在途请求流，所以 5 个客户端相当于对共享后端并行推动 5 条流水线。

- **EFS Bursting 没有被限流。** 全新 EFS 起步即满 burst credit；即便 5 客户端各写 ~1.5 GB（每阶段合计 ~7.5 GB），
  credit 也没耗尽，所以 Bursting 保持与 Elastic 同速（这里甚至略快）。Bursting 只有在**持续**高吞吐、credit 耗尽后才有限流风险。
- **EFS Elastic 与 S3 Files** 均在单客户端时间的 ~2% 以内 —— 干净的聚合扩展，5 客户端未触及竞争墙。
- **JuiceFS** 绝对值最慢（两阶段都约为 EFS/S3 Files 完成时间的 ~1.7×），但关键在于其**共享 Redis 元数据在 5 客户端下
  并未成为竞争瓶颈** —— 相比单客户端的每客户端变慢仅 ~1.02–1.07×。每个文件仍需一次 Redis 往返加一次 S3 对象写，
  这解释了 JuiceFS 单文件更慢，但 Redis 从容承载了 5 客户端并发的元数据负载。

**按并发完成时间排序（两阶段一致）：EFS Bursting < EFS Elastic ≈ S3 Files < JuiceFS。**
在全新文件系统上、5 客户端并发时，EFS Bursting 既最快又最省钱（无单独吞吐费）；JuiceFS 原始速度垫底但扩展干净，
其成本取决于那台专用 Redis 节点（见 4-way 报告的成本章节）。

## 成本估算（月度费用，us-east-2）

按数据量 **1 TB / 10 TB / 50 TB** 三档，拆分「存储费 / 读写流量费 / Redis 元数据费 / 月总计」四项估算（格式同单客户端 4way 报告，1 TB = 1024 GB）。

**单价（us-east-2 官方列表价）：**
- EFS Standard 存储：$0.30/GB·月（Bursting 与 Elastic 存储单价相同）
- EFS Elastic 吞吐：写 $0.06/GB + 读 $0.03/GB
- S3 Standard 存储：$0.023/GB·月；S3 Files 高性能存储层：$0.30/GB·月
- S3 Files 计量：写 $0.06 / 读 $0.03 每 GB
- S3 PUT $0.005/千次、GET $0.0004/千次
- c7i.4xlarge 按需 $0.714/小时 × 720 小时 + 30 GB gp3 = **$516.48/月**（JuiceFS 独占 Redis 固定成本）

**假设：** 每月写入 = 存储该容量（1 次全量写）+ 每月读 1 次全量；JuiceFS 默认 4 MiB 块 → 1 TB≈262,144 对象、10 TB≈2,621,440、50 TB≈13,107,200（写=PUT、读=GET）；JuiceFS 的 Redis 独占一台 c7i.4xlarge 全天候运行。

**说明：**
- EFS Bursting 无单独吞吐费（已含在存储费），是纯存储成本最优的 EFS 形态；Elastic 按读写流量另收费。
- S3 Files 底层 S3 存储便宜，但叠加 $0.30/GB·月的高性能存储层后，总成本反而与 EFS 相当甚至更高。
- **JuiceFS 的 TCO 反转**：数据只存 S3 Standard（$0.023/GB·月）极便宜，但独占的 Redis 节点是每月约 $516 的固定成本。小容量（1 TB）时该固定成本占绝对大头，JuiceFS 最贵；随容量增大固定成本被摊薄，10 TB 起 JuiceFS 总成本已远低于 EFS/S3 Files。**规模越大，JuiceFS 越划算。**
- 本表含存储 + 读写流量 + 请求 + Redis 计算，不含数据传输费；实际元数据节点可调优或共用以进一步降本。
- ⚠️ 单价可能随时间变化，实际以 AWS 官方定价页为准。
